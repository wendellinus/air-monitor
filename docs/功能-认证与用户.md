# 功能-认证与用户

## 功能：登录、注册、刷新、退出

入口：`/api/v1/auth/password-key`、`/api/v1/register`、`/api/v1/login`、`/api/v1/refresh`、`/api/v1/logout`

实现：前端可以先获取密码传输公钥，再发起注册或登录；账号注册写入用户表；登录校验密码后签发 access token 和 refresh token；刷新接口轮换 refresh token；退出时拉黑当前 access token 并撤销该用户全部 refresh token。

核心文件：`apps/api/src/modules/auth/auth.controller.ts`、`apps/api/src/modules/auth/auth.service.ts`、`apps/api/src/modules/auth/jwt.strategy.ts`、`apps/web/src/shared/auth.ts`

思路：把登录态拆成短期 access token 和可轮换 refresh token，兼顾接口鉴权和可控失效。

注意：登录、注册、重置密码都兼容明文密码和加密密码两种传输方式；刷新令牌复用会触发整用户令牌撤销；后端依赖 Redis 做 access token 黑名单。

## 功能：当前用户信息、个人资料、语言设置

入口：`/api/v1/user/me`、`/api/v1/user/me/profile`、`/api/v1/user/me/locale`

实现：登录后用户可以读取自己的基础信息、更新个人资料和语言设置；前端会基于这些数据渲染后台身份信息和多语言文案。

核心文件：`apps/api/src/modules/user/user.controller.ts`、`apps/api/src/modules/user/user.service.ts`、`apps/api/src/modules/user/user.repository.ts`、`apps/web/src/ui/admin/profile-settings/*`

思路：把“我自己”的接口和后台管理别人账号的接口分开，避免职责混杂。

注意：资料更新包含用户名唯一性校验；语言设置会影响后台文案显示。

## 功能：收藏城市

入口：`/api/v1/user/favorites/cities`、`/screen` 收藏面板、`/api/v1/admin/users/favorites/cities`

实现：普通用户可以维护自己的收藏城市；大屏会直接读取收藏列表并支持切换；后台可以查看和删除用户收藏记录。

核心文件：`apps/api/src/modules/user/user.controller.ts`、`apps/api/src/modules/user/admin-user.controller.ts`、`apps/api/src/modules/user/user.service.ts`、`apps/web/src/ui/screen/hooks/use-screen-favorites.ts`

思路：收藏是用户个性化能力，既服务大屏快捷访问，也给后台提供运维清理入口。

注意：依赖 `City` 和 `UserFavoriteCity` 关联数据；删除收藏是按用户和城市双键处理。

## 功能：后台用户管理

入口：`/api/v1/users`、`/api/v1/users/search`、`/api/v1/admin/users/*`、`/admin/users`

实现：后台支持用户列表、搜索、详情、状态切换、重置密码、角色修改和软删除；禁用或重置时会联动撤销登录态。

核心文件：`apps/api/src/modules/user/admin-user.controller.ts`、`apps/api/src/modules/user/user.service.ts`、`apps/api/src/modules/user/user.repository.ts`、`apps/web/src/ui/admin/users/*`

思路：用户管理的 HTTP 层放在 admin controller，真正的规则都收口到 service 和 repository。

注意：状态变更、密码重置、角色调整都可能影响当前会话；删除是软删除，不是物理删库。

---

## 功能：后台用户详情与用户级权限裁剪

入口：`/api/v1/admin/users/:id`、`/admin/users/:id`

实现：后台用户详情页除了展示账号基础信息，还支持在同一页面编辑用户名、启停状态、重置密码、软删除，以及对“该角色原本拥有的权限”做用户级裁剪；保存时后端会分别校验操作者是否具备资料编辑权限和权限裁剪权限。

核心文件：`apps/api/src/modules/user/admin-user.controller.ts`、`apps/api/src/modules/user/user.service.ts`、`apps/web/src/ui/admin/users/hooks/use-admin-user-detail.ts`

思路：角色权限仍然作为主权限来源，用户详情页只负责在具体用户层面做精细化收口，避免把权限模型拆成完全独立的两套体系。

注意：用户级只能裁剪该角色已经拥有的权限，不能额外授予新权限；禁用、删除、密码重置都会联动撤销 refresh token；软删除后用户名会被归档改名，避免唯一键冲突。

## 功能：角色权限

入口：`/api/v1/user/me/permissions`、`/api/v1/admin/permissions/roles/:role`、`/admin/permissions`

实现：系统内置权限定义、角色默认权限和用户级 denied 权限；前端路由守卫、菜单渲染和后台页面操作按钮都依赖权限结果决定可见性和可操作性。

核心文件：`apps/api/src/modules/permission/permission.service.ts`、`apps/api/src/modules/permission/permission.controller.ts`、`apps/web/src/ui/admin/permissions/*`、`apps/web/src/ui/admin/layout/admin-route-guard.tsx`

思路：以角色权限为主，用户级权限只做裁剪，减少权限模型复杂度；`admin` 默认强制同步为全量权限，`operator` 和 `user` 允许在默认集合基础上做增补或裁剪。

注意：权限树分 `menu` 和 `action` 两层；更新角色权限时要同时关注前端菜单、路由守卫和接口守卫；用户级 denied 权限只会从角色已拥有的权限中扣减。
