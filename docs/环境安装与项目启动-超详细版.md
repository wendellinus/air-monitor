## 这份文档解决什么问题

当你第一次接手这个仓库时，通常会同时遇到几类问题：

- 本机缺少运行时环境，不知道先装什么
- 看到了 monorepo，不确定应该在哪个目录执行命令
- 不清楚数据库和 Redis 是自己装还是 Docker 起
- 拿到了 `.env`，但不知道应该放到哪里
- 不知道 `pnpm bootstrap:dev` 到底做了什么
- 启动后前后端分别访问哪个地址
- 登录账号从哪里来
- 出错之后不知道从哪一层开始排查

这份文档就是把这些问题一次性展开说清楚。

## 项目是什么结构

这个仓库是一个 monorepo，核心目录如下：

```text
air-monitor/
├─ apps/
│  ├─ api/         # NestJS 后端
│  └─ web/         # React + Vite 前端
├─ packages/
│  └─ shared/      # 前后端共享包
├─ docs/           # 项目文档
├─ docker-compose.yml
├─ package.json
└─ pnpm-workspace.yaml
```

理解这个结构很重要，因为后面你看到的大部分命令都是在仓库根目录执行的，而不是单独进入 `apps/api` 或 `apps/web`。

仓库根目录负责：

- 管理 workspace
- 统一执行 `pnpm` 脚本
- 启动 Docker 基础设施
- 执行 Prisma 相关命令

## 本地必须具备的软件

### 1. nvm

`nvm` 用来安装和切换 Node.js 版本。项目文档约定使用 `Node.js 22.18.0`，所以先装 `nvm`，再装 Node，比直接在系统里随便装一个 Node 版本更稳。

安装命令：

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
```

安装完成后要做的事：

- 关闭当前终端再重新打开
- 或者手动 `source` 你的 shell 配置文件

验证方式：

```bash
command -v nvm
```

能输出 `nvm`，说明可用。

### 2. Node.js

安装并切换版本：

```bash
nvm install 22.18.0
nvm use 22.18.0
nvm alias default 22.18.0
```

验证方式：

```bash
node -v
```

期望看到类似：

```text
v22.18.0
```

为什么要统一版本：

- 避免某些依赖在低版本 Node 下安装失败
- 避免本地和别人环境不一致导致同一命令结果不同
- 减少 `pnpm install`、`vite`、`nest`、`prisma` 的兼容性问题

### 3. pnpm

这个项目明确要求只使用 `pnpm`，不要换成 `npm` 或 `yarn`。

启用方式：

```bash
corepack enable
corepack prepare pnpm@latest --activate
```

验证方式：

```bash
pnpm -v
```

### 4. Docker Desktop

本项目默认使用 Docker 启动本地依赖服务：

- PostgreSQL
- Redis

为什么推荐 Docker：

- 不需要你自己手动安装和初始化数据库
- 团队环境更统一
- 出问题时更容易按文档复现

安装完成后，务必先打开 Docker Desktop，再执行任何依赖 Docker 的命令。

验证方式：

```bash
docker info
docker compose ps
```

如果 `docker info` 都失败，后面的 `pnpm dev:infra` 和 `pnpm bootstrap:dev` 也一定跑不通。

### 5. Git

你需要 Git 来完成：

- 拉取仓库
- 切换分支
- 更新代码
- 查看改动

验证方式：

```bash
git --version
```

## 第一次接手项目时的推荐顺序

推荐你按照下面这个顺序来做，而不是想到哪一步就跳到哪一步：

1. 安装运行环境
2. 拉取代码
3. 安装依赖
4. 放置私发的环境文件
5. 启动 Docker
6. 执行一键启动
7. 打开 Swagger 和前端页面确认
8. 使用 `.env` 中的初始账号登录后台

这个顺序的好处是，一旦哪一步出错，你能更快判断问题在“系统环境”“项目依赖”“环境变量”“Docker”“数据库迁移”还是“前端代理”。

## 拉取项目代码

在你准备好的工作目录执行：

```bash
git clone <你的仓库地址>
cd air-monitor
```

进入仓库后，可以先确认当前目录正确：

```bash
pwd
ls
```

你应该能看到：

- `apps`
- `packages`
- `docs`
- `package.json`
- `pnpm-workspace.yaml`

如果这些文件夹和文件不存在，通常说明你还没进入项目根目录。

---

## 安装项目依赖

在项目根目录执行：

```bash
pnpm install
```

这一步会把 workspace 需要的依赖装到本地。

如果这里失败，优先排查下面几项：

- `node -v` 是否是团队约定版本
- `pnpm -v` 是否可用
- 网络是否可访问 npm 源
- 是否误用了 `npm install` 或 `yarn`

装完后你通常会看到：

- 根目录出现 `node_modules`
- lockfile 保持为 `pnpm-lock.yaml`

## 环境文件到底怎么处理

这是最容易搞错的一步。

这个项目的真实环境变量不建议直接靠模板文件手填，而是由项目维护者私发。

你需要把私发的环境文件放到下面两个位置：

```text
apps/api/.env
apps/web/.env
```

注意事项：

- 如果你拿到的文件扩展名不是 `.env`，要先重命名
- 如果你拿到的是压缩包，解压后再放到对应位置
- 如果你只有一个后端 `.env`，那前端地图相关功能可能不会正常工作
- `.env.example` 只是字段参考，不是最终运行配置

为什么要分成两份：

- `apps/api/.env` 给 NestJS API 使用
- `apps/web/.env` 给 Vite 前端使用

### 后端环境文件中最关键的字段

下面这些是后端启动最常见、最关键的字段：

```env
NODE_ENV=development
PORT=8080
TZ=Asia/Shanghai
DATABASE_URL=postgresql://postgres:123456@127.0.0.1:5432/your_db?schema=public&sslmode=disable
REDIS_URL=redis://127.0.0.1:6379/0
JWT_ACCESS_SECRET=...
JWT_REFRESH_SECRET=...
JWT_ISSUER=...
INITIAL_ADMIN_USERNAME=...
INITIAL_ADMIN_PASSWORD=...
INITIAL_OPERATOR_USERNAME=...
INITIAL_OPERATOR_PASSWORD=...
```

这些字段分别决定：

- API 监听端口
- 数据库连接
- Redis 连接
- JWT 签发和校验
- 初始后台账号

### 前端环境文件中最关键的字段

前端最常见的是：

```env
VITE_AMAP_KEY=...
VITE_AMAP_SECURITY_JS_CODE=...
```

如果 `VITE_AMAP_KEY` 没配：

- 前端依然可能能打开
- 但地图组件通常不会正常显示

### 如何确认环境文件放对了

至少确认下面两条命令能看到文件：

```bash
ls apps/api/.env
ls apps/web/.env
```

如果终端提示文件不存在，就先不要继续往后执行。

## 一键启动命令到底做了什么

最常用的一条命令是：

```bash
pnpm bootstrap:dev
```

它不是“只启动前后端”这么简单，而是会串起来执行一整套本地启动准备流程。

从当前脚本逻辑看，它会做这些事情：

1. 检查 `pnpm` 是否存在
2. 检查 Docker 是否可用
3. 检查 `apps/api/.env` 和 `apps/web/.env` 是否存在
4. 从 `apps/api/.env` 读取 `DATABASE_URL` 和 `PORT`
5. 启动 Docker 中的 Postgres 和 Redis
6. 等待 Postgres 和 Redis 就绪
7. 按 `DATABASE_URL` 中的数据库名自动建库
8. 执行 Prisma Client 生成
9. 执行 Prisma migrations
10. 执行 seed
11. 构建共享包
12. 检查 API 端口是否已被占用
13. 启动整个开发环境

这就是为什么第一次启动时，优先推荐用 `pnpm bootstrap:dev`，因为它比你手动一条条执行更不容易漏步骤。

## 什么时候用手动分步命令

如果你不想一次跑全流程，或者你正在排查具体哪一步出问题，可以手动拆开执行。

### 1. 只启动数据库和 Redis

```bash
pnpm dev:infra
```

这个命令适合用来先确认基础设施是不是正常。

确认方式：

```bash
docker compose ps
```

通常你应该能看到 PostgreSQL 和 Redis 容器处于运行状态。

### 2. 执行数据库迁移

```bash
pnpm prisma:migrate:dev
```

这个命令用于把 Prisma migration 应用到本地数据库。

如果这里失败，最常见的问题是：

- `DATABASE_URL` 写错
- Postgres 没启动
- 数据库用户名或密码不对
- 本机 5432 端口不是你以为的那个数据库

### 3. 执行种子数据

```bash
pnpm prisma:seed
```

这个命令通常用于创建初始后台账号。

账号来自 `apps/api/.env` 中的：

```env
INITIAL_ADMIN_USERNAME=
INITIAL_ADMIN_PASSWORD=
INITIAL_OPERATOR_USERNAME=
INITIAL_OPERATOR_PASSWORD=
```

如果用户已存在，seed 通常会跳过，不覆盖历史密码。

### 4. 启动前后端

```bash
pnpm dev
```

这个命令会并行启动 workspace 中的开发服务。

如果你只想单独启动某一端：

```bash
pnpm dev:api
pnpm dev:web
```

## 启动成功后去哪里验证

### 1. 先看 Swagger

打开：

```text
http://localhost:8080/api/docs
```

如果 Swagger 能打开，说明后端至少已经成功监听端口并完成基础启动。

### 2. 再看前端首页

打开：

```text
http://localhost:5173
```

如果页面能打开，说明 Vite 前端基本启动成功。

### 3. 再看大屏页面

打开：

```text
http://localhost:5173/screen
```

如果页面打开但地图区域异常，优先检查 `apps/web/.env` 中的高德 Key。

### 4. 再看后台登录页

打开：

```text
http://localhost:5173/admin/login
```

使用 `apps/api/.env` 中的初始账号登录。

## 为什么改了 API 端口之后前端会出问题

前端开发代理默认写在 `apps/web/vite.config.ts`，通常代理到：

```ts
'/api': 'http://localhost:8080'
```

这意味着：

- 后端默认跑在 8080 时，前端可以直接通过代理访问 API
- 如果你把 `apps/api/.env` 里的 `PORT` 改成别的端口，但没同步改前端代理，前端请求就会打到错误地址

所以只要你修改了后端端口，就要同时检查：

- `apps/api/.env` 的 `PORT`
- `apps/web/vite.config.ts` 里的代理目标

## 常见故障排查

### 1. `pnpm: command not found`

原因通常是 `pnpm` 还没启用。

执行：

```bash
corepack enable
corepack prepare pnpm@latest --activate
```

然后重新开一个终端，再试一次。

### 2. `docker` 命令报错或 Docker 不可用

先确认 Docker Desktop 已经启动。

执行：

```bash
docker info
```

如果这里就失败，不要继续排 Prisma 或项目代码，先把 Docker 问题解决。

### 3. `PORT 8080 is already in use`

说明本机已有别的进程占用了 8080。

处理思路：

- 结束占用 8080 的进程
- 或者修改 `apps/api/.env` 里的 `PORT`
- 修改后记得同步调整前端代理

### 4. 数据库连不上

优先检查：

- `pnpm dev:infra` 是否已经执行
- `docker compose ps` 中 PostgreSQL 是否在运行
- `apps/api/.env` 的 `DATABASE_URL` 是否写对
- 用户名、密码、数据库名、端口是否与本地容器一致

### 5. 登录不上后台

优先检查：

- `pnpm prisma:seed` 是否执行过
- `apps/api/.env` 中的初始账号字段是否真的有值
- 该用户是否已经存在但密码是旧密码

必要时可以重新确认 seed 输出日志。

### 6. 地图不显示

优先检查：

- `apps/web/.env` 是否存在
- `VITE_AMAP_KEY` 是否配置
- 前端是否重启过

Vite 读取环境变量通常需要重启 dev server 才会生效。

### 7. 部分业务接口报第三方服务错误

这通常不是“项目启动失败”，而是第三方凭证没有配置完整。

最常见涉及：

- `QWEATHER_*`
- 高德地图相关配置
- 提供商额度监控相关配置

第一次接手时，可以先接受“项目能启动，但部分外部数据为空”的状态，先保证本地开发链路通顺。

## 建议的最小成功标准

如果你是第一次启动项目，不要一上来就要求所有外部接口都正常。

更现实的最小成功标准是：

1. `pnpm install` 成功
2. `apps/api/.env` 和 `apps/web/.env` 放对位置
3. `pnpm bootstrap:dev` 成功跑起来
4. 能打开 Swagger
5. 能打开前端页面
6. 能使用初始账号登录后台

做到这一步，说明你的本地开发环境已经基本成型。

之后再继续处理：

- 地图显示
- 和风天气数据
- 城市检索
- 空气质量
- 预警同步
- 提供商额度监控
